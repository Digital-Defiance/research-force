## Scope and hard constraints (read first)

- Produce four source files plus their tests:
  - `infra/cloudflare/resources.ts` — pure data: the full planned resource set. No side effects, no I/O, no network, no `process` access at module load.
  - `infra/cloudflare/provision.ts` — turns `resources.ts` into an ordered list of planned Cloudflare API calls, with a `--dry-run` CLI that prints them and never touches an account.
  - `infra/secrets.ts` — pure data: the single source of truth listing every secret (and the non-secret vars that are installation inputs) per Worker.
  - `tools/check-secrets.ts` — CLI that reports which secrets are missing, using a local presence check only (no account access).
- NO network calls, NO Cloudflare account access, NO deployment anywhere in this task. `provision.ts` must have `--dry-run` that only prints the plan. Any apply/live branch that is scaffolded must be clearly gated behind an explicit non-default flag and must throw/refuse rather than call out when invoked under test or dry-run — it must not be reachable from `--dry-run` or from the test suite.
- Do NOT touch `apps/app/web/src/files/**` or `apps/app/src/files/**` (another agent owns tasks 30.6–30.8). Stay within `infra/` and `tools/`. Reading `apps/*/wrangler.jsonc`, `apps/app/src/env.ts`, `apps/submit/src/index.ts`, `apps/dl/src/index.ts`, and `apps/app/src/mail/providers/graph.ts` is allowed (read-only) and already done during planning.
- Match existing conventions: ESM, `type: module`, TypeScript 6 with the strict `tsconfig.base.json` settings (`verbatimModuleSyntax`, `isolatedModules`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `composite`), `node:` prefixed built-ins, no new runtime dependencies, CLI entrypoint guarded by the `process.argv[1] === fileURLToPath(import.meta.url)` pattern used in `tools/check-specs.ts` and `tools/certify-profile.ts`.

## Design decisions (made here, grounded in the repo)

1. **Where the TypeScript lives / project wiring.** Nothing under `infra/` is TypeScript today (only JSON), and the boundary checker in `scripts/check-boundaries.mjs` assigns an owner only to files under `packages/`, `apps/`, `tools/`; files under `infra/` get `undefined` (no boundary rule). But `tsc -b` only type-checks files that a composite project includes, and the `tools` project (`tools/tsconfig.json`) includes only `src/**/*.ts`, `*.ts`, `types/*.d.ts` under `tools/`. Decision: make the `infra` TypeScript files part of the existing `tools` project rather than creating a new project, because `tools/check-secrets.ts` must import `infra/secrets.ts` and the simplest boundary-clean way is one project. Add `"../infra/cloudflare/resources.ts"`, `"../infra/cloudflare/provision.ts"`, and `"../infra/secrets.ts"` (or `"../infra/**/*.ts"`) to the `include` array of `tools/tsconfig.json`. The infra files import nothing from `@researchforce/*`, so no new project references are needed and the boundary checker stays satisfied (infra files have no owner; `tools/check-secrets.ts` imports only a relative `../infra/secrets.ts`, which resolves to owner `undefined` and is therefore unrestricted).
   - Rationale for not adding a dependency on the Workers' own `Env` interfaces: `apps/app/src/env.ts` and the per-Worker `Env` interfaces are not exported from a `@researchforce/*` package and `tools` must not import app internals across a relative path that the boundary checker would reject (`tools` may not import `app`). So the secret list in `infra/secrets.ts` is authored as plain data mirrored from those `Env` types, with a code comment citing the source files. Correctness is enforced by a test assertion listing the expected names, not by a type import.

2. **`resources.ts` shape — pure data, discriminated unions.** Export a single top-level constant (e.g. `export const cloudflareResources`) typed as a `readonly` tree of plain objects, plus the exported TypeScript types for each resource kind. No functions that perform I/O; a few pure helper constants (origins, hostnames) are fine. Model production and staging as two entries of the same shape so provisioning can iterate both, matching the two-environment split already in every `apps/*/wrangler.jsonc` (production names like `rf-core`, `rf-private`; staging names like `rf-core-staging`, `rf-private-staging`, and staging hostnames `staging.researchforce.org` / `dl-staging.researchforce.org` as found in the configs). The resource set (names and specifics taken from the wrangler configs, `design.md` §"Cloudflare configuration"/"Hosts"/lines 127–130, 1298–1301, and the referenced requirements) is:
   - **D1 databases:** `rf-core`, `rf-search`, `rf-public` (and `-staging` variants). Note current `database_id`s are placeholder UUIDs; resources.ts encodes the database *names* and bindings, not the placeholder IDs. (Req 1.1 — Workspace foundation.)
   - **R2 buckets:** `rf-private` and `rf-public` (+ `-staging`). On `rf-private`:
     - CORS: allow method `PUT` from origins `https://app.researchforce.org` (Workspace) and `https://researchforce.org` (apex), allowed headers `content-length`, `x-amz-checksum-sha256`, `if-none-match`, exposed header `ETag` (from README "Files and protected downloads" and design line 1301; the apex submission origin is included per the task text "PUT from the Workspace and apex origins").
     - Lifecycle rule: abort incomplete multipart uploads after 1 day (design lines 483, 1301).
     - `r2.dev` public access: off. No custom domain. (Req 25.2; design line 513.)
     - On `rf-public`: `r2.dev` off, custom domain `files.researchforce.org`. (Design lines 127, 517.)
   - **Zone/edge rules** (zone `researchforce.org`):
     - `www` → apex redirect rule.
     - On `files.researchforce.org`: a Cache Rule "bypass cache" and a response-header rule adding `Content-Security-Policy: sandbox` and `X-Content-Type-Options: nosniff` (design line 127; Req 25.3 — public copy unreachable/consistent).
     - WAF: a **disabled** block rule for `submit` (the Public_Traffic_Budget block rule, encoded as disabled per task text), and a rate-limiting rule shared by `submit` and `dl` (design lines 128–130, 141; Req 28.5).
     - Bot Fight Mode: off. Always Online: off. (Req 45.18; design line 992 — apex never uses Bot Fight Mode/challenge pages.)
   - **Worker custom domains:** `app.researchforce.org` → `rf-app`, `submit.researchforce.org` → `rf-submit`, `dl.researchforce.org` → `rf-dl` (design lines 128–130). `rf-ops` has no public route (design: "`rf-ops` has no fetch handler or public route") — encode it with no custom domain.
   - **Access application** on `app.researchforce.org`: session duration 24 hours; cookie settings HttpOnly, `SameSite=Lax`, binding cookie enabled; identity providers one-time PIN, Google, GitHub; an Access list `rf-members`; and an allow policy referencing `rf-members` (design lines 319–320, 129; Req 1.1/1.3).
   - **Turnstile widget:** managed mode (design line 985; Req 31.3 context — the submit form Turnstile).
   - Encode each item with enough structured fields that `provision.ts` can derive a concrete API call, but do not invent account/zone IDs — represent those as named placeholders (e.g. `{ zoneId: "<zone-id>" }` or a `ResourceContext` the provisioner would be given) so nothing implies real account access.

3. **`provision.ts` — planner + dry-run CLI.** Export a pure function (e.g. `planApiCalls(resources, context)`) returning an ordered `readonly PlannedCall[]`, where each `PlannedCall` is `{ method, endpoint, summary, body? }` with `method` an HTTP verb, `endpoint` a Cloudflare REST path template (account/zone IDs shown as `:accountId` / `:zoneId` placeholders, never resolved), `summary` a one-line human description, and `body` a redacted payload summary (never secret values). Order calls by dependency: buckets before their CORS/lifecycle/custom-domain; zone rules after; Access list before its policy before the application; Worker custom domains after Workers exist. The CLI (guarded by the `import.meta.url` check) supports:
   - `provision.ts --dry-run [--env production|staging]` → prints the plan (default both envs or production; pick one and state it) as human-readable lines `METHOD endpoint — summary` plus, under each, an indented payload summary; exits 0; performs no network or account access. Absence of `--dry-run` must NOT perform a live apply in this task: either require `--dry-run` (error otherwise) or gate any apply path behind an explicit `--apply` flag that immediately throws "live provisioning is not implemented in task 48.1" (decision: require `--dry-run`; unknown/missing flags print usage and exit non-zero, mirroring `check-specs.ts`). Output format is plain text to stdout; a `--json` option MAY print the same plan as JSON for the test to parse (decision: include `--json` so the test asserts on structured output rather than scraping text).

4. **`infra/secrets.ts` — single source of truth, pure data.** Export `export const workerSecrets` as a `readonly` record keyed by Worker name (`rf-app`, `rf-submit`, `rf-dl`, `rf-ops`), each entry listing `secrets` (set via `wrangler secret`) and `vars` (plaintext installation inputs in wrangler `vars`), with a short note per entry. Enumerated from `apps/app/src/env.ts`, `apps/submit/src/index.ts`, `apps/dl/src/index.ts`, the wrangler configs, and `apps/app/src/mail/providers/graph.ts` (`GraphProvider.fromEnv` reads the Graph names). Exact lists:
   - **rf-app** — vars (non-secret, already in `apps/app/wrangler.jsonc`): `WORKSPACE_ORIGIN`, `DOWNLOAD_ORIGIN`; installation vars to set: `R2_ACCOUNT_ID`, `PRIVATE_BUCKET_NAME` (from `env.ts` + README). Secrets: `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `DOWNLOAD_HMAC_KEY`, `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `GRAPH_TENANT_ID`, `GRAPH_CLIENT_ID`, `GRAPH_CERT_KEY`, `GRAPH_CERT_THUMBPRINT`, `SENDING_ADDRESS`. (From `apps/app/src/env.ts`: `ACCESS_TEAM_DOMAIN`/`ACCESS_AUD` are documented as secrets; the five Graph/`SENDING_ADDRESS` names come from `graph.ts`. `WORKSPACE_ORIGIN` is a var, not a secret, per the wrangler config — classify it as a var.)
   - **rf-submit** — secret: `TURNSTILE_SECRET` (from `apps/submit/src/index.ts` `Env`). Cross-Worker DO bindings (`BUDGET`, `MAILER`) are config bindings, not secrets — do not list them as secrets.
   - **rf-dl** — vars: `WORKSPACE_ORIGIN` (already in `apps/dl/wrangler.jsonc`). Secret: `DOWNLOAD_HMAC_KEY` (same value as rf-app; note the shared-value requirement). (From `apps/dl/src/index.ts` `Env`.)
   - **rf-ops** — no secrets and no vars (no fetch handler, no env reads; `apps/ops/src/index.ts` is empty of env). Encode an empty entry with a note so the file documents that rf-ops has none.
   - Add a code comment on each list naming the source file(s), and a comment noting production and staging require independent credentials/secrets (README: "Production and staging must use separate credentials").

5. **`tools/check-secrets.ts` — local presence check CLI.** Import `workerSecrets` from `../infra/secrets.ts`. Report which secrets are missing using a **local** source only — no account access. Decision: accept a provided presence source and default to parsing a dotfile, following how the repo already uses `.dev.vars` (README) — read the names present in a `.dev.vars`-style file (KEY=... lines; values ignored, only key presence matters) and/or `process.env`. CLI: `check-secrets.ts [--vars <path-to-.dev.vars>] [--worker <name>] [--env production|staging]`; prints, per Worker, the secrets that are not present locally; exits non-zero when any required secret is missing (so it can gate), 0 when all present. It never prints secret values — only key names and present/missing status. Factor the pure comparison (given a set of present key names + the `workerSecrets` data → missing list) into a small exported function so the test drives it without filesystem state, mirroring how `check-specs.ts` exports `checkSpecs`/`repositoryStatus` for its tests. Wire an npm script `secrets:check` into root `package.json` (`node --import tsx tools/check-secrets.ts`), consistent with `profile:certify` / `release:check`.

## Notes and assumptions

- Cloudflare REST endpoint path templates in `provision.ts` are written from general Cloudflare API knowledge as illustrative, dependency-ordered placeholders (`:accountId`/`:zoneId` never resolved); they are not validated against a live account in this task and real activation is task 48.4/48.6. If an endpoint path is uncertain, prefer a clearly-labeled placeholder path plus an accurate `summary` over a guessed exact path — the test asserts ordering, placeholder-safety, and no-secret-leak, not exact Cloudflare URLs.
- `resources.ts` intentionally does not carry real `database_id`s or account/zone IDs; the current wrangler `database_id`s are placeholder UUIDs (README: "Database UUIDs are deliberate placeholders ... Task 48 provisions real resources and replaces these IDs"). Keeping IDs out of the encoded plan is consistent with the no-account-access constraint.
- Secret classification (secret vs var) follows the wrangler configs and `env.ts` comments: `WORKSPACE_ORIGIN`/`DOWNLOAD_ORIGIN` are vars (present in `wrangler.jsonc`); `ACCESS_TEAM_DOMAIN`/`ACCESS_AUD` and the Graph/`SENDING_ADDRESS` names are secrets. If a reviewer prefers `R2_ACCOUNT_ID`/`PRIVATE_BUCKET_NAME` classified as vars vs secrets, the `env.ts` comment groups them with the S3 credential secrets but they are identifiers, not secrets — the plan classifies them as installation vars with a note; adjust if the design doc is later read to require otherwise.
- No new npm dependencies are introduced; `tsx` (already a devDependency) runs the CLIs, matching every other `tools/*.ts` script.
