# Compatible software releases

This directory is the software compatibility catalog. Research releases and public snapshots are separate domain objects (task 66).

`development.json` is a mutable development baseline, generated from the current source files and ordered migration journals. There are currently **no released software versions and no supported production backup formats**. The baseline declares exact current schema ranges, source, Worker configuration, package/lockfile and migration SHA-256 fingerprints, all five Workers, the Resource_Profile version, supported operating profiles, and a seven-day accepted recovery-window default. It does not assert that any Worker is deployed. Actual provider version IDs, schema heads, old-consumer leases, cutover time and accepted window belong in the observed deployment inventory.

Use Node 22.16 or newer (the local recovery-copy API requires it). Commands from the repository root:

```sh
npm run release:write
npm run release:check
npm run release:rehearse
npm run release:plan -- infra/releases/development.json infra/recovery/deployment.example.json
node --import tsx scripts/deploy.ts --preflight apps/app/wrangler.jsonc infra/releases/development.json infra/recovery/deployment.example.json
```

`release:write` refreshes only the development baseline. Run it after changing application, domain, database, build/upgrade tooling or migration sources. `release:check` verifies fingerprints, exact journal coverage, schema ranges and released-reader retention; CI requires it. A released manifest is never regenerated against a new checkout. Keep its original sources/artifacts and execute source checks in that release's checkout. Provider-version rollback must use the observed immutable version IDs and compatible declarations, not an old version selected by date alone.

When preparing a distinct candidate, `npm run release:seal -- <candidate-id>` creates a new immutable candidate JSON file with exclusive creation. Existing identities and path traversal are refused. A candidate can be reviewed and tested for staging; it cannot authorize production. Production planning requires a released manifest. Promotion, observed provider inventory, built-artifact binding, all mandatory staging evidence and activation remain tasks 48.4/68.4. The current tools never deploy Workers, buy a plan, publish research or promote a candidate to a released version.

## Rollout and recovery

Use one release ID per immutable candidate/release. Declare every schema revision and migration digest, with separate expansion and contraction heads and explicit `baseline`, `expand` or `contract` phases. `baseline` identifies inherited history; it does not make destructive changes safe. Every Worker declares its combined read/write range for each database it actually uses. Missing app/submit/download dependencies are refused. Update declarations only with tests demonstrating both old and new consumer behavior. Source fingerprints are evidence of code identity, not proof of compatibility by themselves.

The enforced plan order is expansion, compatible consumers, bounded backfill, verification, read-path switch, recovery-window wait, contraction. Preflight rejects an old deployed consumer that cannot use the expanded schema. Existing databases must have verified adopted history; a matching file name is insufficient and existing data migrations are never blindly replayed. Adoption builds the declared DDL prefix independently and compares it with the actual schema before recording migration hashes.

The local SQLite expansion adapter commits schema work and its history together. It hashes existing table rows through iteration, preserves original column names/types/defaults/key constraints, and checks existing indexes/triggers. An unsafe expansion rolls back. A contraction requires the exact expanded schema, the target consumers everywhere, zero old-consumer/retry leases, verified backfills matching the exact declared version/limits, an ended recovery window (the greater of the target and previously accepted window), and an installation-specific fresh restore proof completed within 24 hours. The proof names the target schemas, backup ID and verification-artifact digest, and requires counts, hashes, references, authorization, consent, suppression and bootstrap identity checks. A completed contraction can be reconciled without replaying its SQL.

The window is policy, not a timer automatically authorizing data loss. Supply a provider-observed inventory and genuinely verified restore artifacts through the later production deployment adapter. A hand-written JSON claim is not independent infrastructure attestation. The local contract script refuses production/staging inventories and unrelated database files. `infra/recovery/restore-proof.example.json` deliberately fails validation until real checks, time and verification digest are supplied.

Rollback checks keep the current database schema and permit only a declared prior safe Worker release whose ranges still fit it. If contraction retired an old schema, that old Worker cannot be rolled back. `node --import tsx tools/release.ts rollback|forward <manifest> <inventory>` produces the compatible Worker-only recovery plan. A forward target cannot downgrade schema. Public rebuilding stays denied; full restore, suppression reapplication and release gates remain required.

## Backfill and rehearsal boundaries

`runBackfillSlice` is the local transactional reference adapter for registered keyset backfills. It bounds effects to at most 500 rows and 128,000 encoded bytes, with one bounded lookahead row; it uses non-empty ordered TEXT or safe INTEGER primary keys, fingerprints definitions and specifications, rejects changed definitions/stale generations, and commits effects/cursor/generation atomically. Final completion requires a successful verification callback. A source row larger than the bound is refused for a fragment-aware adapter; it is never truncated or skipped. The registered `search-fts-v1` repair uses those slices to populate pre-existing documents missing from the inherited FTS-creation migration. Reset and first effects/cursor share a transaction, and final FTS integrity/content checks must pass. Run it only on quiescent rehearsal data; a live provider upgrade needs the later D1/job adapter and compatible index generation. Register versioned code and a bounded verification method when implementing each real backfill. The callbacks execute trusted migration code, never SQL or code from a backup/upload.

`release:rehearse` creates a fresh temporary directory and seven isolated database runs: core 10/9/8, search 3/2/1 and public 0. Each run seeds representative pre-upgrade rows where applicable, reopens a real SQLite recovery copy, verifies/adopts its history, upgrades and checks preservation, seeds all implemented kinds, and verifies indexing and repeat execution. The report records source checkpoint, applied tags, copy hash and limitations. Temporary paths printed by the command are disposable local files; no active dev database or D1 instance is used.

For a database in that report, `npm run schema:expand -- --local infra/releases/development.json core /absolute/rehearsal/core-10.sqlite` reconciles expansion. The `schema:backfill` command has the same local arguments and executes one registered search-index slice, returning its checkpoint. Repeat until complete. The corresponding contract command additionally requires inventory and restore-proof paths. These scripts restrict input to matching working files in a completed local rehearsal, exclude its recovery copies, and never accept `--remote`.

Historical migration checkpoints are not invented released schemas. Generic preservation tests and the field-migration rehearsal cover the immutable field-version storage introduced in 57.3. There is no production backup reader to retire today. The catalog enforces current/two-prior released-schema reader declarations where such versions exist, and refuses unsupported headers. Until 58.1 registers authenticated transforms, `checkRelease` refuses any manifest claiming an operational backup reader. Local SQLite copies do not certify independent encrypted recovery, RPO/RTO, D1 CPU/limits, provider rollout, bootstrap identity ownership or production authorization/consent/suppression. Those release gates remain mandatory.
